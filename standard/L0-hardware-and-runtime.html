Reality2 Standard — Layer 0: Hardware and runtime

Date: 2026-08-04

Introduction

Reality2 runs on hardware that has nothing in common. A sensor node with sixty-four kilobytes of memory and a solar cell, a phone in someone's pocket, a virtual machine with no radio at all — these are peers in the same mesh, and each one is expected to behave identically to every other from Layer 1 upward.

That is only possible if the differences between them are confined to one place. Layer 0 is that place. Below it, everything is particular: this radio, this allocator, this way of writing a firmware image. Above it, nothing is particular at all.

So this document is not a hardware specification. It names no processor, no radio part and no product, and it sets no power budget. It specifies what a platform owes the layers above it — the small set of facilities that Layers 1 to 7 assume without ever asking for them, and the declaration by which a platform states which of the optional ones it has.

Two things follow from that, and both shape what is written here.

An unstated assumption is the dangerous kind. Where a facility is assumed but never specified, each implementer supplies it differently, both implementations pass their own tests, and the divergence appears at Layer 3 or Layer 5 — far from the platform that caused it. Clause 10 therefore states, plainly, what Reality2 has not decided at this layer. An absence recorded is survivable; an absence inferred is not.

A platform describes itself in parameters, never in products. A class defined as "a single-board computer" stops being checkable the moment single-board computers change. A class defined as "provides an allocator, one gigabyte of memory, hosts Layer 7, always receptive" can be checked by anyone, today and in ten years. Clause 8 is built on that distinction.

1 Scope

This document specifies the facilities a Reality2 platform provides to the layers above it.

It defines the minimum capability that qualifies hardware as a device, and the relaying obligation that every device carries.

It specifies the isolation a platform maintains at the trust boundary.

It defines the declaration by which a platform states its parameters, and the capability classes those parameters place it in.

It establishes what conformance to this layer consists of and how it is checked.

It identifies the facilities that higher layers assume and that Reality2 has not specified.

It does not specify processors, radio parts, power budgets, enclosures or physical form, and it names no product. It does not specify transport bindings, which are Layer 1.

3 Terms and definitions

For the purposes of this document, the terms and definitions given in Reality2 Standard — Terminology and core definitions apply, together with the following.

3.1 platform

hardware together with the software that adapts it, providing the facilities specified in Clause 5 to the layers above

Note 1 to entry: In the normal case a platform hosts one hive, or one part of a hive whose parts run on separate processors. A platform capable of isolating them can host several hives at once, each in its own sealed environment (Layer 5, 4.3.5); most platforms cannot, and nothing obliges any platform to.

3.2 platform adaptation

part of an implementation that differs between platforms, isolated so that everything above it is identical on every platform

Note 1 to entry: The relationship is that of a device driver to an operating system. The layers above a platform adaptation cannot tell which hardware is beneath it, and are not written to find out.

3.3 platform declaration

statement of the parameter values in 8.2 for a particular platform

3.4 capability class

set of parameter values, identified by a number, that a platform declaration can satisfy

Note 1 to entry: A class is a threshold, not a category of hardware. Anything meeting the values of a class is in that class, whatever it is made of.

3.5 monotonic time source

time source whose reported value never decreases while the platform remains powered

Note 1 to entry: A monotonic time source is not required to relate to wall-clock time, to any epoch, or to any other platform's time source.

3.6 key-bearing platform

platform that retains trust-group key material across loss of power

Note 1 to entry: Being key-bearing and hosting Layer 5 are independent. A platform can hold key material placed on it before deployment and use it to validate frames while performing no membership operation of its own.

3.7 duty-cycled platform

platform that is unpowered or unreceptive for scheduled intervals during normal operation

Note 1 to entry: The complement is an always-on platform, which is receptive whenever it is in service.

3.8 wake window

interval, agreed in advance, during which duty-cycled platforms are simultaneously receptive

4 Devices and relaying

4.1 What counts as a device

4.1.1 Hardware qualifying as a device shall be able to:

a) receive frames of the Reality2 wire protocol (Layer 4);

b) validate a received frame's integrity check; and

c) originate frames, relay frames, or both.

4.1.2 Hardware that transmits data without processing the Reality2 wire protocol shall not be presented as a device.

Note 1 to entry: Such hardware attaches to a device as a peripheral. This constrains what may be claimed, not what may be built.

Verification: submit a well-formed frame and one with a corrupted integrity check. A conforming device accepts the first and rejects the second.

4.2 Relaying is the default, and stopping is a declaration

4.2.1 A device shall relay frames addressed to others, except as permitted by 4.2.2.

4.2.2 A device in capability class 1 (8.3) that is power-constrained may cease relaying.

4.2.3 A device that has ceased relaying shall carry the constrained-origin marking on every frame it originates.

Note 1 to entry: The constrained-origin marking is a flag bit of the wire format, specified at Layer 4. The marking means "this origin will not relay for you" and nothing else — a fully capable hive that happens to run on small hardware does not carry it.

Note 2 to entry: 4.2.3 exists because a device that stops relaying without saying so is indistinguishable, from every other device's position, from one that has failed. The mesh then spends effort routing through something that will never forward. Ceasing to relay is legitimate; ceasing silently is not.

Verification: transmit a frame addressed to a third party within range of the device under test. Either it retransmits, or its own originated frames carry the constrained- origin marking.

4.3 Identity

4.3.1 Every device shall have an identity unique among devices, which persists across loss of power.

4.3.2 A device whose platform does not satisfy 5.5.1 may have its identity generated elsewhere and installed before deployment.

Note 1 to entry: 4.3.2 is why 5.5.1 is conditional. A platform without a usable entropy source is not excluded from Reality2; it is excluded from manufacturing its own keys, and receives them instead.

5 What a platform provides

Every facility in this clause is reached across the platform adaptation boundary (3.2). A higher layer obtains it without knowing, and without being able to discover, what provides it.

5.1 Transport access

5.1.1 A platform shall provide at least one Layer 1 transport binding.

5.1.2 For each binding it provides, a platform shall expose operations to transmit a frame, to receive a frame, to configure the binding's parameters, and to place the binding into and out of a low-power state.

5.1.3 A platform having no radio hardware shall provide those operations over its available network transports.

5.1.4 No layer above shall be required to know which transport technology underlies a given binding.

Note 1 to entry: A platform providing no binding at all can host no hive, since a hive is externally visible by definition and there would be nothing for it to be visible on.

Note 2 to entry: 5.1.3 is what makes a platform with no radio an ordinary participant rather than a special case. The same requirement, differently arranged, would have produced a standard with a permanent exception in it.

Verification: exercise transmit and receive on each declared binding through the abstraction, with no reference in the calling code to the underlying technology.

5.2 A monotonic time source

5.2.1 A platform shall provide a monotonic time source (3.5) with a resolution of one second or finer.

5.2.2 The monotonic time source shall be readable without network access.

5.2.3 A platform shall not present its monotonic time source as wall-clock time, and shall not require its value to be comparable with any other platform's.

Note 1 to entry: The layers above use this source for elapsed intervals — how long since a neighbour was heard, how stale a path has become. A counter starting at zero on each start satisfies every such use. Requiring more would have excluded the platforms Reality2 most wants to include, in exchange for nothing.

Verification: read the source twice with a delay between reads. The second value is not less than the first, and the difference corresponds to the interval elapsed.

Not specified: what happens across loss of power. Whether the source resumes, resets, or is unavailable after power is lost is not specified. An implementer shall not assume that an interval spanning a power cycle is measurable. A count of restarts is not a duration. (Clause 10.)

5.3 Storage that survives power loss

5.3.1 A platform shall provide storage retaining its contents across loss of power, sufficient at least for the identity required by 4.3.1.

5.3.2 A key-bearing platform (3.6) shall retain its trust-group key material in that storage.

5.3.3 A platform shall not require network access to read or write that storage.

Note 1 to entry: Membership of a trust group is durable, and re-establishing it requires a person. A platform that forgets its key material when power is removed cannot rejoin unattended, whatever else it can do.

Verification: write, remove power, restore power, read back.

5.4 Dynamic memory, where it is needed

5.4.1 A platform hosting Layer 5 or above shall provide a dynamic memory allocator.

5.4.2 A platform hosting no layer above Layer 4 need not provide one.

Note 1 to entry: Layers 1 to 4 are specified so that they can be implemented with static allocation and fixed-size buffers alone. This is a deliberate constraint on those layers, not an accident of them being simple — it is what allows the smallest hardware to carry mesh traffic for everyone else.

Verification: exercise a platform through Layers 1 to 4 with dynamic allocation disabled.

5.5 Random numbers, where keys are made

5.5.1 A platform generating key material shall provide a cryptographically secure random number generator.

5.5.2 A platform not providing one shall not generate key material.

5.5.2a Key material shall be generated only while the platform's entropy source meets the conditions under which it is conforming.

5.5.2b A platform whose entropy source is conforming only under stated conditions shall refuse to generate key material while those conditions are unmet.

Note 0 to entry: 5.5.2 asks whether a platform can generate conforming key material, and on a dominant embedded platform the honest answer is yes, while something else is running. Measured from vendor source: its hardware generator produces true random numbers only while the radio subsystem is enabled or an ADC is sampling, and is otherwise pseudo-random only. So the constraint is one of timing, not of capability — and a hive minting its persona at first boot before starting a radio produces a perfectly well-formed 32-byte identity from a pseudo-random source. Nothing errors, nothing is malformed, and the device is weak for its whole life.

Note 1 to entry: No conformance test that inspects the result can see this, which is why the obligation is on the moment rather than on the output: the output of a weak generator and a strong one are indistinguishable by inspection, so a negative control is not constructible here at all (01-terminology.md 4.5). The practical consequence an implementer will not otherwise derive: the radio starts before trust boots. (Added 2026-08-02, PROVISIONAL(supervisor), finding SS213, from an implementation that read 5.5.2 correctly, answered it correctly, and would still have minted a weak identity.)

Note 1 to entry: 5.5.2 and 4.3.2 are one rule seen from two sides. A platform without adequate entropy does not improvise — it receives key material made where there was enough.

Verification: identify the entropy source behind the generator. A generator seeded from a value fixed at build time, from the device identity, or from the monotonic time source alone does not satisfy 5.5.1.

5.6 Sensors and peripherals

5.6.1 A platform providing sensors or general-purpose input and output shall expose operations to enumerate them and to read and write them.

5.6.2 A platform providing none of these shall report them as unsupported, and shall not report an error.

5.6.3 A platform should present sensor values in SI units.

Note 1 to entry: The distinction in 5.6.2 carries weight. Unsupported is a fixed property of the platform, which a higher layer can act on once and remember. Error is a passing condition, which a higher layer will retry — for as long as it keeps being told to.

Note 2 to entry: This clause is known thin, and the thinness is now a recorded gap rather than a settled scope: the working corpus carries a hardware-capability registry contract this document never absorbed — a namespace of capability tokens with binding kinds, role-sets under a disjoint-union invariant, and a fail-closed rule that an unlisted token grounds nothing — machinery that is CI-wired and consumed today. Whether it enters this document, a companion, or stays implementation territory is register item Q38 (found by the provenance audit, 2026-08-01).

Note 3 to entry: Note 2's gap has since been measured from the implementing side, and the indicator row is the worked example. Three capability names for one hardware function were found in use in one catalogue, one of them with no provider at all and appearing only in requirement position — an ensemble requiring a capability nothing supplied. FORMATS.md Clause 6 holds no indicator contract, so by 6.1 all three names are deployment-local and carry no interop claim, however established one of them looks. The consequence to state here is that a hardware function every board image is obliged to carry has no agreed name, and the standard is silent rather than permissive about it — the silence is Q38's, not a licence. (Added 2026-08-04, PROVISIONAL(standard), on composer-lane measurement.)

5.7 Applying a firmware image

5.7.1 A platform shall provide the means by which a validated firmware image is applied to it.

5.7.2 How an image is applied shall not be visible above the platform adaptation boundary.

Note 1 to entry: Only the final act is a platform facility. How an image is carried, authorised and validated is specified elsewhere and is identical everywhere. What differs between platforms — writing a partition, replacing files, swapping code in a running system — differs entirely below this line.

Note 2 to entry: Two further physical affordances are required of a device by upper layers and are recorded here so a platform designer sees them early: a local physical action by which the claim state is reset (Layer 5, 4.4 — a device without one can never change owner), and a recovery facility beneath the stack by which possession restores a working image (Layer 6, 5.5). Both are stated where their authority models live.

5.8 Nothing particular escapes upward

5.8.1 The behaviour of Layers 1 to 7 shall be identical on every conforming platform.

5.8.2 A platform shall not require any higher layer to behave differently on account of the hardware beneath it.

Note 1 to entry: A platform difference visible above this boundary is a defect in the platform adaptation. It is never a property of Reality2, and it is never a reason for a higher layer to acquire a special case.

Verification: a conformance suite for any higher layer passes unmodified on two platforms in different capability classes.

6 Isolation at the trust boundary

The trust boundary lies between Layer 4 and Layer 5. Where a platform hosts both sides of it, the platform is what keeps them apart.

6.1 Code implementing Layers 1 to 4 shall not have access to:

a) trust-group private keys;

b) sentant state; or

c) management credentials.

6.2 Data passing from Layer 4 to Layer 5 shall be validated before it is processed.

6.3 Data passing from Layer 4 to Layer 5 shall carry no trust material.

6.4 Where the two sides are hosted on separate processors, 6.1 to 6.3 apply to the link between them exactly as within one processor.

6.5 An implementation should enforce 6.1 by construction — so that below-boundary code cannot name the items listed — rather than by a check made while running.

Note 1 to entry: 6.1 forbids material that conveys trust. It does not forbid below-boundary state that is merely secret. A value generated locally at start, never transmitted, and used only for a local decision grants no authority over anything and is permitted below the line. The test is whether an item conveys trust, not whether it is secret.

Note 2 to entry: This clause is why one mesh can carry many trust groups. A device relays for groups it is not a member of and could not join, because the code doing the relaying was never able to reach anything that would let it. The property is structural, and it is what "shared mesh, private data" means in practice.

Verification: enumerate what the below-boundary code depends on. A dependency reaching any item in 6.1 a) to c) is non-conforming whether or not it is exercised while running.

7 Availability

7.1 A platform shall declare itself always-on or duty-cycled (3.7).

7.2 A duty-cycled platform shall not assume any peer is receptive outside a wake window (3.8).

7.3 A duty-cycled platform shall state three intervals: the shortest permitted between wake periods, the longest permitted, and the shortest it may adopt without being instructed to.

7.4 A duty-cycled platform shall not adopt an interval shorter than the shortest permitted, whatever instruction it receives.

Note 1 to entry: The three intervals in 7.3 are different quantities with different owners. The first protects the energy source and belongs to whoever deployed the hardware. The second bounds how stale the data may become and belongs to whoever depends on it. The third is the limit of the platform's own discretion. Collapsing them into one number loses the ability to say which one was violated.

Note 2 to entry: The declaration required by 7.1 is what lets the routing layer hold a frame for a platform that is asleep instead of treating it as unreachable. A sleeping device and a failed device are indistinguishable without it, and the mesh will treat both as failed.

Note 3 to entry: Availability and energy state are separate declarations. A platform whose energy supply is healthy can still be duty-cycled, and a platform running low on energy is not thereby duty-cycled.

Verification: instruct the platform to adopt an interval shorter than its stated shortest permitted. A conforming platform does not adopt it.

8 Declaring what a platform is

8.1 The declaration

8.1.1 A platform shall publish a platform declaration (3.3).

8.1.2 A platform declaration shall state a value for every parameter in 8.2.

8.1.3 A platform declaration shall not identify a class by a product name, a board name or a vendor name.

Note 0 to entry: The declaration answers one question: what must a platform tell the layers above it, and why must they be told rather than assume? Every parameter is here because some other part of this standard makes a decision that is wrong without it — not because the parameter describes something interesting about hardware. Parameters P9 to P13 and subclauses 8.5 and 8.6 were drafted as one piece after six independent findings, from three implementations and two platforms, each arrived at the same clause from a different direction (SS61, SS68, SS90, SS113, SS115, SS135). That convergence is the evidence the question is real: a declaration assembled one finding at a time becomes a list of accidents, and six parties needing the same clause is a different fact from six parties each wanting a field.

Note 1 to entry: A declaration naming a product ceases to be checkable when the product changes, and says nothing to anyone who does not have one. A declaration in parameters can be checked by someone holding different hardware entirely — which is the only kind of check this standard can require.

8.2 Parameters

8.2.1 A platform declaration shall state:

# Parameter Stated as
P1 Processing capability memory available to the implementation, and persistent storage available to it
P2 Low-power state whether the low-power state any energy figure depends on is implemented in the software as shipped
P3 Transports the Layer 1 bindings provided, by technology
P4 Peripheral power whether power to sensors and peripherals is gated
P5 Timebase across power loss whether any timebase survives loss of power
P6 Highest layer hosted the highest layer this platform runs
P7 Key-bearing whether the platform retains trust-group key material (3.6)
P8 Availability always-on or duty-cycled, with the three intervals of 7.3 where duty-cycled
P9 Update slots whether the platform provides image slots for the update model of Layer 6, 5.4; where it does, how many and the usable size of each
P10 Update-path write boundary whether the storage the update path writes through enforces a boundary that path cannot cross, and which regions lie outside it
P11 Image read-back whether a stored image can be read back in pieces bounded by available memory
P12 Recovery substrate whether the structures the update arrangement itself depends on — the slot layout, and the code that chooses a slot — can be written by the platform's own install path, and whether the integrity check applied before writing covers them
P13 Position observability whether the platform can report to the layers above it that no valid image-position record exists, or whether its boot path writes one where it finds none

8.2.2 An energy or duration figure stated for a platform shall name the parameter values it was measured or calculated against.

Note 1 to entry: P2 separates a hardware capability from a fact about software on purpose. A low-power state the hardware supports and the shipped software never enters contributes nothing to any energy figure, and a declaration that cannot express the difference will be read as though it does.

Note 2 to entry: P5 determines whether an obligation expressed as a duration can be met at all. An obligation counted from a known start is satisfiable while powered; an obligation fixed to an absolute point in time is not satisfiable on a platform whose timebase does not survive power loss. (Clause 10.)

Verification: an energy or duration figure naming no parameter values, and a declaration omitting any parameter, are each non-conforming. Neither can be checked by anyone outside the organisation that wrote it.

8.3 Capability classes

8.3.1 A platform whose declaration satisfies the values below is in the corresponding capability class.

Class P1 memory P1 storage P6 highest layer Typical availability
1 ≥ 64 kB ≥ 256 kB 4 either
2 ≥ 64 kB and ≥ 512 MB across two processors ≥ 256 kB and ≥ 4 GB 7 mixed — see 8.3.4
3 ≥ 1 GB ≥ 8 GB 7 always-on
4 ≥ 1 GB ≥ 10 GB 7 always-on
5 ≥ 100 MB available to the implementation ≥ 50 MB available to the implementation 7 duty-cycled by the host system

8.3.2 A platform in a capability class shall provide at least the following capacities.

Structure Class 1, and the Layer 1–4 part of class 2 Classes 3 and 4, and the Layer 5–7 part of class 2 Class 5
Deduplication cache 128 entries 4 096 entries 1 024 entries
Neighbour table 32 entries 256 entries 64 entries
Packet log 256 entries unbounded 1 024 entries

8.3.3 A platform satisfying the values of more than one class may declare any of them, and shall meet 8.3.2 for the class it declares.

8.3.4 Where a platform in class 2 runs Layers 1 to 4 and Layers 5 to 7 on separate processors, the part running Layers 1 to 4 shall be always-on, and the part running Layers 5 to 7 may be duty-cycled independently of it.

Note 1 to entry: The two processors of a class 2 platform are one hive, not two devices, and the identity, beacon and capability set belong to the hive. Whether the second processor is currently powered changes what the hive can do; it does not change who the hive is.

Note 2 to entry: A class 4 platform has no radio and reaches the mesh over network transports alone. Constraints on such a platform arising above the trust boundary are stated at Layer 5.

Note 3 to entry: The classes are thresholds, and 8.3.3 says so directly. A platform is not in class 1 because of what it is made of; it is in class 1 because of what it declared. Anything meeting class 3's values is in class 3.

Verification: measure the allocated capacity of each structure. A neighbour table below the stated minimum is non-conforming even where no deployment has yet filled one.

8.4 Form of the declaration

8.4.1 A platform declaration shall be published in a form a third party can read without possessing the platform.

The following form satisfies 8.1 and 8.2. It is illustrative and not the only permitted form.

platform-declaration: 1
  P1  memory: 512 MB          storage: 4 GB
  P2  low-power-state-implemented: yes
  P3  transports: [lora, ble, wifi]
  P4  peripheral-power-gated: yes
  P5  timebase-survives-power-loss: no
  P6  highest-layer-hosted: 7
  P7  key-bearing: yes
  P8  availability: duty-cycled
      shortest-permitted: 5s
      longest-permitted: 30m
      shortest-self-selected: 30s
  P9  update-slots: 2               usable-size-each: 1600 kB
  P10 update-path-write-boundary: yes
      outside-boundary: [slot-layout, boot-chooser]
  P11 image-read-back: yes
  P12 recovery-substrate-writable: yes    covered-by-pre-write-check: no
  P13 position-observability: manufactured-on-boot
  class-declared: 2

Note 0 to entry: The example declares P12 covered-by-pre-write-check: no — a platform whose install path can rewrite the structures recovery depends on and does not verify them. That combination is permitted and must be stateable, because it is the common case and because a reader needs to see it: it is the arrangement in which a single unverified write removes the rollback the rest of Layer 6 relies on. A declaration that could not express it would leave every such platform looking like every other.

Note 1 to entry: The example states P5: no alongside P8 intervals expressed in time. That combination is permitted and is common. It means the intervals are measured from a known start while the platform is powered, and that no obligation fixed to an absolute point in time can be met by it. (Clause 10.)

8.5 Declaring what a platform does not have

8.5.1 Where a platform does not provide a facility this document requires, its declaration shall state the shortfall, naming the facility.

8.5.2 A declared shortfall shall name the obligations of other parts that the platform therefore cannot meet.

Note 1 to entry: Until 8.5 the declaration could describe only what a platform has, so a platform lacking a required facility had no vocabulary for its own shape and was simply non-conformant — with the effect that the honest description and the dishonest one were equally unavailable. The instance: a hive hosted in a browser without persistent storage, for which a page reload is a loss of power, so it cannot hold a persona across one. It is a legitimate hive and it cannot meet 5.3. A standard that cannot say so gets told nothing, and the layers above it discover the shortfall by failing.

Note 1a to entry: The warrant for 8.5 is a night of measurement, not the browser case above. On 2026-08-02 this standard's implementing lanes found six platform facts that changed clauses — a slot geometry with no floor, a write boundary no layer required declaring, an image that could not be read back, verification covering a payload and not the substrate beneath it, a boot path that manufactures an update record, and a checksum covering one field of a record and not another. Every one had to be discovered by measurement — a partition table grepped, a vendor source read, a checksum's scope traced through header comments — and none of them could have been read off a platform declaration, because the declaration could describe only what a platform has. The facts that mattered were all of the form this platform cannot, and there was no place in the declaration for a sentence of that shape. (Rationale added 2026-08-02, PROVISIONAL(supervisor); the clause it justifies is 8.5, findings SS61, SS68, SS90, SS113, SS115, SS135.)

Note 2 to entry: 8.5.2 is the load-bearing half. A shortfall stated without its consequences reads as a small omission, and the reader who needs it is the one deciding whether to deliver a persona, an update, or a key to that platform. Naming the obligations lost turns a gap in a table into a fact another layer can act on.

8.6 The update facilities

8.6.1 A platform declaring the capability of Layer 6, 5.4.1 shall provide at least two image slots, each able to hold a complete image for its target, and persistent storage for the records Layer 6 requires that lies outside both.

8.6.2 A platform whose declaration states no write boundary (P10) shall not claim conformance to Layer 6, 4.2.2 by construction.

8.6.3 A hive on a platform that cannot report the absence of a valid image-position record (P13) shall not treat that record as evidence that an update was applied, without the corroboration Layer 6, 5.4.2b requires.

Note 1 to entry: 8.6.1 states the floor relationally rather than in bytes, because an image size is a per-platform fact and any figure stated here would be wrong for most platforms and unreachable for some. What does not vary is the shape: two slots, because 5.4.3's rollback without external help needs the prior image to still exist, and a records region outside both, because a record inside a slot is erased by the write it exists to describe.

Note 2 to entry: 8.6.2 gives 4.2.2's by construction an enabling mechanism and a name. That clause is satisfiable only where the storage offers a boundary the update path cannot cross — partition handles, a protection region, separate storage. On a platform whose storage is one flat writable space to all on-device software it cannot be satisfied by construction at all, only by convention, which 4.2.2 rejects. Before P10 the standard was silent on which platforms were which, so both kinds claimed the same conformance.

Note 3 to entry: 8.6.3 answers a measured case rather than a hypothetical one. On a dominant embedded platform, in the layout the reference board uses, the boot path constructs and writes an image-position record where it finds none — correct, documented behaviour — so the no valid record condition exists for less than one boot and never reaches the application at all. A clause requiring such a platform to report that condition would be requiring something it structurally cannot do. The resolution is not to weaken the requirement but to make the platform say so and require a second source: P13 declares it, and 5.4.2b's corroboration of the record against the slots is that second source. 01-terminology.md 5.4 arriving as a conformance requirement rather than as advice. (Added 2026-08-02, PROVISIONAL(supervisor); findings SS61, SS68, SS90, SS113, SS115, SS135.)

Note 4 to entry: What this subclause deliberately does not add. A seventh parameter is implied by the same evidence — which fields of a platform's own records its validity check covers, after a vendor format was measured whose checksum covers a record's sequence and not its state. It is left out because no finding demanded it: it was observed, not needed, and a parameter added because it would round out the model is an unproven guard in prose. It is named here so its absence is legible as a decision.

9 Conformance

Every requirement of this document is demonstrated by conformance evidence of one of the three classes of 01-terminology.md, 3.10 — behavioural, by construction, or by declaration. A requirement whose evidence is by construction is not thereby optional: the demonstration is an inspection a third party can perform without the implementer's cooperation, and its absence is non-conformance exactly as a failed behavioural test is. Behavioural evidence for any requirement of this document carries the control 01-terminology.md 4.2 to 4.5 requires — the same procedure run against a case the requirement excludes, giving a distinguishable non-satisfying result attributable to the requirement under test; a demonstration that could not have come out any other way is not evidence. (Added 2026-08-02, PROVISIONAL(supervisor); the control sentence added the same day, finding SS183.)

9.1 A platform conforms to this document where it:

a) meets Clause 4;

b) provides every facility of Clause 5 that its declaration requires of it;

c) maintains the isolation of Clause 6 for every trust boundary it hosts;

d) meets Clause 7 for the availability it declares; and

e) publishes a declaration under Clause 8 and meets the capacities of the class it declares.

9.2 Every requirement of this document shall be verifiable by a party having no relationship to the implementer.

Note 1 to entry: 9.2 is not a formality and it removed material from this document while it was being written. A requirement checkable only with the authors' own equipment, fixtures, or judgement is not a requirement of this standard — it is an arrangement between people who already know each other, and the reader this standard is written for is not one of them.

Note 2 to entry: A declaration that is not published cannot be checked, which is why 8.1.1 requires publication rather than merely requiring that a declaration exist.

10 What is not decided at this layer

This clause states gaps and contains no requirements. It is here because a gap that is recorded can be worked around, and a gap that is left silent is filled by each implementer differently and discovered when two of them meet.

10.1 The execution model. Reality2 does not specify whether a component invoked by the runtime may block; whether a deadline or time budget applies to such an invocation; whether an invocation may be re-entered; or what becomes of other components while one is running. The absence of a statement decides none of these — it is an absence, not a permission. The question is stated for decision at Layer 7 (its 10.1), where the sentant's determinism property already implies single-threaded execution per sentant; blocking, budgets and re-entrancy remain open there.

What this costs an implementer: a component that has to wait — for a sensor to settle, for a bus transaction to finish — cannot be assumed safe to write as a blocking call, and cannot be assumed unsafe either. Until this is decided, a platform and the components it hosts are joined by a convention nobody has written down.

10.2 Durations that span a power cycle. No facility here measures elapsed time across a loss of power, and P5 exists so a declaration says plainly whether its platform could. An obligation fixed to an absolute point in time cannot be met on a platform declaring P5: no, while an obligation counted from a known start can be. Across this standard the kinds are now marked at their sites: every obligation of Layers 0 to 4 is counted from a known start, and the one absolute-time judgement — certificate validity — is named as such where it occurs (Layer 5, 6.1). What a P5: no platform does about that one is Layer 5's open question, not a labelling gap.

10.3 Time as something a component can ask for. Resolved above this layer: at Layer 7, anything non-deterministic — time included — reaches a sentant only through a plugin named in its definition, so the plugin binding is the declaration. What remains here is only that this document's monotonic time source (5.2) is a platform facility, not a declarable one — which no longer needs to change.

10.4 Protecting key material at rest. 5.3.2 obliges a key-bearing platform to retain key material across power loss. Nothing here specifies protecting that material from someone holding the hardware. A platform that is key-bearing, unattended and physically exposed is under-specified by this document, and the silence is not an assurance that retention alone is sufficient. (This gap now has a named downstream consumer: Layer 5, 5.3.2 permits persisted derived keys only sealed under a hardware-rooted secret, and inherits from here the undecided question of how that facility is declared and checked — when this settles, both clauses move together.)
